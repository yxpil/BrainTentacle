BrainTentacle BIT is a desktop agent hub: an Electron shell, a Rust core (bit-core), and a React UI. Point it at any model and chat in streaming — let the AI call local tools, write scripts on the fly, and save conclusions as memory and skills. Secrets are masked before they reach the model, data never leaves this machine, and every call leaves an audit trail.

It gets the AI out of the chat box

More than Q&A. Tools run on your machine, scripts are written by the AI itself, and conclusions persist across sessions on your disk. Everything below works offline, with zero accounts required.

Tool registry

Register, toggle and call tools; local interpreters are auto-detected (Python / Node / PowerShell / Perl / Julia…). The AI writes a script that reads args on stdin and prints results to stdout, and it becomes a tool — hot-reloaded, with success rate and average latency shown for each one.

Three extension layers

A local plugin with one plugin.json, any standard MCP server, or your own long-running process hosted directly. All three end up in the same tool registry, and the AI calls them identically.

Memory & skills

The AI saves things on its own via the built-in add_memory and skill tools: today’s gotcha, this project’s conventions, the way a given flow works — reused next time, no manual organizing.

Sub-agents

With Autopilot on, todos are dispatched to sub-agents and worked in parallel; plan goals and task progress are visible and deletable on the Memory page at any time.

Long tasks don’t get cut off

Close the window and it lives in the tray; right-click the task panel to inspect chat turns, background commands, sub-agents and active goals. Long commands auto-background and keep running when you switch away; enable “prevent system sleep” if needed.

Remote access & gateway

Turn on remote access and a full HTTP API is exposed (default 0.0.0.0:8600), including an OpenAI-compatible /v1/chat/completions endpoint — your desktop model and tools become a gateway on the LAN.

MCP client & server

It is an MCP client (Streamable HTTP or stdio, to import external tools) and a standard MCP server at POST /mcp with automatic protocol version negotiation — Claude Desktop and MCP Inspector connect out of the box.

Terminal mode

After install, type bit in any terminal for the TUI: no window, no single-instance lock, no listening port — made for SSH and headless boxes.

Three layers of extension, light to heavy

Local plugins are the lightest lift, MCP plugs into an existing ecosystem, and WorkWith hosts your own process directly. All three feed the same tool registry, and the AI treats them the same.

01

Local plugins: one folder, one plugin.json

Drop the plugin folder into toolhomes/plugins/ under your data dir and hit “rescan plugins” — tools, prompts, skills, memories and scheduled jobs go live together. You can also declare long-running services, standalone pages and chat-page icon entries in the same file.

02

MCP servers: paste an mcpServers block

Same config format as Cursor and Claude Desktop (command + args + env); it can also scan a port range and auto-discover MCP servers already running on your LAN.

{ "mcpServers": { "files": { "command": "npx", "args": ["-y", "@modelcontextprotocol/server-filesystem"] } } }
03

WorkWith: host your own long-running process

Point it at an executable on the Services page and you’re done — the host launches the process, scans its port and wires up MCP automatically. Ports, logs and shutdown are all managed by the host.

The plugin ecosystem: one folder is one new capability

No packaging, no compiling, no host code to touch. Drop a plugin.json into the plugins directory and tools, prompts, skills, memories, jobs, services and standalone pages are handed to the AI at once; hit rescan and your changes are live. Plugins are declarative local files — nothing runs until you download it.

Toolstools[]
Declare one tool the AI can call: parameters described by JSON Schema; the script reads args on stdin and prints results to stdout. It runs on a local interpreter (Python / Node / PowerShell / Perl / Julia…) or in the built-in Rhai sandbox. Every tool shows its success rate and average latency.
Promptsprompts[]
Appended to the system prompt when enabled. Write rules like “this project uses pnpm, not npm” or “lead with the conclusion” into a plugin; install it on another machine and the AI works the same way.
Skillsskills[]
Inject reusable procedures (name + summary), same shape as skills the AI derives on its own. A good way to bake in a troubleshooting checklist or a document template.
Memoriesmemories[]
Injected as long-term facts: this machine’s default working directory, internal hostnames, team conventions — present from install, no need to restate them every chat.
Jobsjobs[]
Run a script on a cadence like every 30m / daily 09:00; the output can be injected into a chosen session so the AI takes over, or just land in the audit log.
Servicesservices[]
Up to 16: the plugin ships a process; the host assigns a port (write 0 for auto, delivered via BIT_PLUGIN_PORT) and manages logs and shutdown. With mcp_mode set to http the port is auto-wired as an MCP server once ready; with stdio the process itself is the MCP server.
Pagespages[] · status_page
Register standalone pages in the sidebar (sandboxed iframe, static src or dynamic url), plus a live status panel on the plugin detail page — dashboards, metrics, health checks all fit.
Chat entrieschat_icons[] · takeover[]
Up to 4 icon entries: tapping one opens the plugin page, or fills a prompt into the composer. Go further and take over built-in buttons (voice / preview / attachments / plan / templates / web / background tasks) with your own entry — Settings is never takeover-able, and built-ins can be restored with one click.
Permissionspermissions[] · bridge
Every capability must be declared up front; undeclared calls are refused outright. Settings lists permissions one by one with individual toggles — exec (run commands) and write (touch any file) are flagged high-risk. Exposing an endpoint (bundled server / page / settings UI) requires a bridge block; tokens are minted at each launch and never ship inside the plugin.

Three steps to get in

01

Find the plugins directory

It’s always toolhomes/plugins/ under your data dir. With BIT installed, the Tools page → Local plugins block shows the full path with a one-click copy.

Windows%APPDATA%\com.bit.hub\toolhomes\plugins\
macOS~/Library/Application Support/com.bit.hub/toolhomes/plugins/
Linux${XDG_DATA_HOME:-~/.local/share}/com.bit.hub/toolhomes/plugins/
02

Drop a folder in

The folder name is the plugin id; the layout must be plugins/<plugin-name>/plugin.json — no extra nesting. Unzip a ready-made bundle here, or write your own plugin.json: it’s the single manifest, and scripts / pages / settings live next to it, referenced by relative path.

03

Hit “rescan plugins”

Tools show up in the tool list immediately; prompts and memories apply from the next chat. Each plugin has its own on/off switch and rescans don’t reset your choices; plugins that fail to load are skipped with a reason listed, never dropped silently.

A minimal manifest that actually runs (tool + prompt + skill + memory + job):

{
  "name": "my-plugin",
  "version": "0.1.0",
  "description": "One line about what this plugin does",
  "tools": [{
    "name": "disk_usage",
    "description": "Disk usage of a given directory",
    "parameters": {
      "type": "object",
      "properties": { "path": { "type": "string", "description": "Directory path" } },
      "required": ["path"]
    },
    "kind": "interpreter",
    "runtime": "py",
    "file": "disk_usage.py"
  }],
  "prompts": ["Always answer in English."],
  "skills": [{ "name": "Disk drilldown", "summary": "Run disk_usage first, then drill down level by level" }],
  "memories": ["Default working directory on this machine is D:/work"],
  "jobs": [{
    "name": "daily-report",
    "schedule": "daily 09:00",
    "runtime": "py",
    "file": "daily.py"
  }]
}

Tool scripts speak the same protocol as hand-written tools — read args JSON on stdin, print results to stdout:

import json, sys, shutil

params = json.loads(sys.stdin.read() or "{}")
total, used, free = shutil.disk_usage(params.get("path", "."))
print(json.dumps({"total": total, "used": used, "free": free}, ensure_ascii=False))

Keys never reach the model. Data never leaves this machine.

Secrets are masked before anything is sent to the AI; risky tools get a second-pass review before they run; every call is replayable afterwards. No account system, no telemetry at all.

Dashed lines = tool call and local restore. Raw values never enter the model context.

HiddenCode masking

Keys, phone numbers, emails and usernames are swapped for placeholders or your own aliases (Alice → Bob) before anything leaves the machine, then restored when a tool runs. Built-in type masks, exact-value matching, custom regex and paste-time scanning are all supported.

L2 PASS review

Before a tool runs, a second model decides Allow / Deny and can override auto-approved tools. If the reviewer is unreachable, calls fall back to manual approval without interrupting normal use.

Audit log

Every tool call and key action is logged and filterable by subject / action / target — afterwards you can reconstruct who touched what, and when.

Data stays local

Chats, memories, skills and settings all live in the local data dir (Windows %APPDATA%\com.bit.hub, macOS ~/Library/Application Support/com.bit.hub) and are gone on uninstall.

Docs & FAQ

Full install notes, the plugin spec, and API / MCP details live in the repo; these are the spots people get stuck on first.

Repo README Wiki · Quick start English README
macOS says it’s “damaged, can’t be opened”

BIT is currently ad-hoc signed (no paid developer certificate), so browser downloads carry a quarantine flag that macOS misreports as “damaged”. The signature itself is fine — just clear the flag:

xattr -cr /Applications/BIT.app

Alternatively, open System Settings → Privacy & Security and click “Open anyway”.

Windows SmartScreen blocked the app

The installer is not code-signed. On first run, click More info → Run anyway. Same for the portable build.

What do I set up on first launch?

Open AI settings → Add provider → pick the protocol (OpenAI / Gemini / Claude), fill in the Base URL and API key, type the model name (or click “fetch from API” to pull the list), then press the play button on the row to activate. Only one provider is active at a time; the rest pause automatically.

How do my tools show up in Claude Desktop?

Turn on remote access and BIT is a standard MCP server: endpoint POST /mcp, with 2024-11-05 / 2025-03-26 / 2025-06-18 auto-negotiated, Mcp-Session-Id sessions and tools/list / tools/call supported. Point your MCP client at http://host:8600/mcp — the auth is the same set used by the remote API.

Where is data stored, and how do I uninstall cleanly?

Windows %APPDATA%\com.bit.hub, macOS ~/Library/Application Support/com.bit.hub, Linux ${XDG_DATA_HOME:-~/.local/share}/com.bit.hub. Deleting that directory wipes everything; if you set BIT_DATA_DIR, that wins.

How do I use it behind a corporate proxy?

Settings → AI settings → Network proxy, three modes: follow system / force direct / custom proxy. Custom supports http / https / socks5 and applies everywhere at once: model requests and update downloads, env vars for child processes like curl / git / npm, and the embedded browser. Address and password are always masked in the UI.

Why is it free forever — and is there any telemetry?

Apache-2.0 open source, every feature free for personal and commercial use: no in-app purchases, no subscriptions, no feature locks, no telemetry — or build it yourself. There is no account system, and the app installs fine offline; the only outbound request is the version manifest check on update.
